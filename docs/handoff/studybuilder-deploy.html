Standing up the Study Builder

An internal web application for the sales team, to sit alongside the existing site on our own server. Everything it needs is below; nothing about the current site changes.

studybuilderbd.mtgroupbio.com

What this is

The Study Builder replaces the current process of hunting through HubSpot and OneDrive for a comparable quote and retyping a Word document. Reps fill in a structured form; it produces two Word files — an internal draft with the pricing workings, and a clean sponsor-facing quote. A feasibility request builder shares the same form and the same database.

It is a Node application rather than PHP, so it cannot be dropped into a folder beside the existing site. It runs as its own service on a local port, with nginx in front of it.

How it fits with the current site

One additional server block. The existing configuration is not edited.

www.mtgroupbio.com → nginx → PHP-FPM  (unchanged)
studybuilderbd.mtgroupbio.com → nginx → 127.0.0.1:3000 → Node

Both hostnames can resolve to the same IP; nginx separates them by server_name. The database is hosted externally (Neon Postgres), so nothing new runs on the box besides the Node process.

What the server needs

RequirementDetail
Node.js Version 20 or newer. Built and tested on 22. Installs alongside PHP without conflict.
Process manager systemd, already present. No need for pm2 or similar.
Outbound HTTPS To Neon (the database) and to HubSpot's API. No inbound access beyond 443.
Disk Under 1 GB including node_modules. Generated documents are not stored.
TLS Let's Encrypt via certbot, same as the main site.

For reference, on a test build the application compiles in about 23 seconds and the server is accepting requests roughly 150 ms after start.

1 DNS

One record, pointing at the server that already serves the site:

studybuilderbd    A    <the server's public IP>

2 nginx

A separate server block, so the existing site's config stays untouched.

server {
    listen 443 ssl http2;
    server_name studybuilderbd.mtgroupbio.com;

    ssl_certificate     /etc/letsencrypt/live/studybuilderbd.mtgroupbio.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/studybuilderbd.mtgroupbio.com/privkey.pem;

    # Word documents are generated on the fly and can take a moment.
    proxy_read_timeout 120s;

    location / {
        proxy_pass         http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade           $http_upgrade;
        proxy_set_header   Connection        'upgrade';
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}

server {
    listen 80;
    server_name studybuilderbd.mtgroupbio.com;
    return 301 https://$host$request_uri;
}

Certificate: certbot --nginx -d studybuilderbd.mtgroupbio.com. It renews itself.

3 The service

# /etc/systemd/system/studybuilder.service
[Unit]
Description=MT Group Study Builder
After=network.target

[Service]
Type=simple
User=studybuilder
WorkingDirectory=/srv/studybuilder
EnvironmentFile=/etc/studybuilder.env
ExecStart=/usr/bin/node node_modules/.bin/next start -p 3000
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target

4 Deploying a new version

cd /srv/studybuilder
git pull
npm ci                 # generates the database client
npm run db:deploy      # applies any new migrations
npm run build
sudo systemctl restart studybuilder

There is a health endpoint at /api/health worth pointing monitoring at. It returns 200 when the application can reach the database and 503 when it cannot, so a failure shows up as down rather than as a page that loads but cannot save anything.

5 Secrets

In /etc/studybuilder.env, owned by root, mode 600. These never go in the repository. 

DATABASE_URL=postgresql://...-pooler...   # pooled, for the app
DIRECT_URL=postgresql://...               # unpooled, migrations only
HUBSPOT_TOKEN=pat-na1-...                 # read-only service key

Two database URLs is not a mistake. Migrations run against a transaction-mode pooler fail on lock acquisition — sometimes only under load — so the migration tooling is pointed at the direct connection deliberately.

! Before the DNS record goes in

The application currently has no login. A subdomain is not private — they get found and guessed — and the internal draft carries our pricing notes, margins and site costs.

Authentication is being built before go-live. Worth knowing now in case you would rather restrict access at the nginx level as well, or put it behind the office IP range for an initial trial.
